# Установка ELE на сервер

ELE поставляется как self-hosted решение (docker-compose): одна копия обслуживает
одну компанию. Ниже — минимальные требования и развёртывание «одной строкой».

## Требования к серверу

| Ресурс | Минимум | Рекомендуется |
|---|---|---|
| ОС | Ubuntu 24.04 LTS | Ubuntu 24.04 / 26.04 LTS |
| CPU | 2 vCPU | 2–4 vCPU |
| ОЗУ | 2 ГБ | 4 ГБ (сборка фронтенда при деплое требует ~1–2 ГБ) |
| Диск | 20 ГБ SSD | 40 ГБ SSD + запас под файлы и резервные копии |
| ПО | `git`, `curl`; Docker Engine 24+ и Compose v2 (скрипт установки поставит сам, если их нет) | то же |

Про диск: помимо ОС и Docker-образов (~2–3 ГБ) место расходуют база PostgreSQL,
загруженные файлы (аватары до 2 МБ, файлы реквизитов до 20 МБ) и резервные копии.
При большом объёме файлов вынесите хранилище в S3 (`ELE_STORAGE_MODE=s3`) — тогда
диск сервера почти не растёт.

Сеть: домен с A-записью на IP сервера, открытые порты **80** и **443** — Caddy
сам получит и продлит TLS-сертификат Let's Encrypt. Локальный файрвол ОС
(ufw/firewalld) скрипт установки откроет сам; **облачный security group в панели
провайдера открывается отдельно** — скрипт до него не достанет.

**Локальный режим без домена (HTTP без TLS).** Если домен не нужен (инстанс во
внутренней сети), оставьте «Домен инстанса» пустым — скрипт определит IP-адреса
сервера и настроит доступ по HTTP (порт 80, без TLS). Внешний IP добавляется
только по подтверждению. ⚠️ В этом режиме вход и данные идут **открытым
текстом** — используйте только в доверенной сети; **не** выставляйте так админку
в интернет.

## Установка «одной строкой»

```sh
curl -fsSL https://raw.githubusercontent.com/alfafamily/ele/main/install.sh | bash
```

Скрипт:
1. проверит Docker и Docker Compose; если их нет — **предложит установить Docker
   автоматически** (официальный скрипт `get.docker.com`; нужен root или `sudo`);
2. склонирует репозиторий в `/opt/ele` (или обновит, если уже есть);
3. если `.env` ещё нет — **интерактивно спросит параметры и создаст `.env` сам**
   (домен, почта/SMTP, режим хранилища, при желании — Яндекс Captcha/ID и первый
   администратор); `DJANGO_SECRET_KEY` и пароль PostgreSQL генерируются
   автоматически. Секреты хранятся только в `.env` и не вводятся через интерфейс;
4. откроет порты **80/443** в локальном файрволе (ufw/firewalld), если он активен;
5. соберёт и поднимет прод-стек: `docker compose -f docker-compose.prod.yml up -d --build`.

Каталог установки можно переопределить: `ELE_DIR=/srv/ele bash install.sh`.

### Два способа создать первого администратора и компанию

Команда установки одна и та же; отличается только, как заполнить шаг «Первый
администратор»:

- **Через Setup Wizard (в браузере).** Оставьте email администратора **пустым**
  (Enter). После старта откройте `https://<домен>` — запустится мастер первичной
  настройки: он создаст администратора и компанию и проверит интеграции.
  В `.env` учётные данные администратора при этом не пишутся.
- **Через терминал.** Укажите email и пароль администратора на шаге установки —
  администратор создастся автоматически при первом старте. **Пароль после старта
  стирается из `.env`** (он нужен только для разового создания учётки).

Секреты интеграций (SMTP, S3, Яндекс) и **адрес инстанса** в обоих случаях
задаются только в `.env` (адрес нужен ещё до старта — по домену Caddy получает
TLS, а Django проверяет `ALLOWED_HOSTS`). Задать домен → HTTPS; оставить пустым →
локальный режим по IP без TLS (см. выше). Изменить позже — правка `.env`
(`SITE_ADDRESS`, `DJANGO_ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `SITE_URL`) +
`up -d` и, для домена, перенастройка A-записи DNS.

### Куда кладётся `.env`

В корень установки — `/opt/ele/.env` (права `600`). Чтобы поменять параметры
позже: отредактируйте файл и примените:

```sh
cd /opt/ele
docker compose -f docker-compose.prod.yml up -d
```

Переменные читаются один раз при старте контейнера — после правки `.env`
обязателен перезапуск (`up -d`). Полный список переменных с пояснениями —
в [`.env.example`](../.env.example).

## Установка вручную (эквивалент)

```sh
git clone https://github.com/alfafamily/ele.git /opt/ele
cd /opt/ele
cp .env.example .env      # заполнить SITE_ADDRESS, ELE_ADMIN_*, секреты
docker compose -f docker-compose.prod.yml up -d --build
```

## Первый вход

- Если в `.env` заданы `ELE_ADMIN_EMAIL` / `ELE_ADMIN_PASSWORD` — администратор
  создаётся автоматически при первом старте.
- Иначе при первом заходе в браузере откроется **мастер первичной настройки**:
  создание администратора, реквизиты компании, проверка интеграций из `.env`.

## Обновление версии

```sh
cd /opt/ele
git pull --ff-only
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d --build
```

Схемные изменения БД применяются миграциями автоматически при старте backend.

Обновления **кумулятивны**: версии можно перепрыгивать (например, с 1.0.2 сразу
на 1.0.9) — при старте backend применит все накопившиеся миграции по порядку за
один проход, поэтапно проходить каждую версию не нужно. Если какой-то релиз
потребует особого порядка обновления, это будет явно указано в его записи в
`CHANGELOG.md`. **Перед обновлением рекомендуется сделать резервную копию** (см.
ниже «Резервное копирование и восстановление») — на случай отката.

## Полное удаление / переустановка с нуля

> ⚠️ **Удаляет все данные без возможности восстановления**: базу PostgreSQL,
> загруженные файлы (при локальном хранилище), TLS-сертификаты. Если данные
> нужны — **сначала сделайте резервную копию**: Настройки → Резервное
> копирование → «Экспорт», и скачайте файл на отдельный носитель (восстановление
> — командой `restore_backup`, см. ниже).

```sh
cd /opt/ele

# остановить и удалить контейнеры, сеть, ТОМА (все данные) и собранные образы:
docker compose -f docker-compose.prod.yml down -v --rmi local --remove-orphans

# удалить каталог установки вместе с .env:
cd / && rm -rf /opt/ele
```

Что удаляют флаги — это две независимые вещи: **`-v`** удаляет **тома** (данные:
БД, файлы, сертификаты), **`--rmi`** удаляет **образы** (сборки/кеш, не данные):

| Флаг `--rmi` | Что с образами |
|---|---|
| *(без флага)* | образы не трогаются — остаются и `ele-*`, и `postgres`/`caddy` |
| `--rmi local` | удаляются только собранные `ele-backend/frontend/cron`; `postgres`/`caddy` остаются в кеше |
| `--rmi all` | удаляются **все** образы стека, включая `postgres`/`caddy` |

В команде выше — `--rmi local`: базовые `postgres`/`caddy` намеренно оставляем в
кеше, чтобы переустановка не тянула их заново из Docker Hub и не упёрлась в лимит
`429`; собранные `ele-*` всё равно пересоберутся из исходников. Чтобы снести
вообще всё, включая базовые образы, — `--rmi all` (переустановка потом заново их
скачает). Данные (тома) в любом случае удаляет `-v`, независимо от `--rmi`.

Если хранилище было **S3** — файлы в бакете этой командой **не удаляются** (они
вне сервера); при необходимости очистите бакет отдельно.

**Переустановка с нуля** — та же команда установки; `.env` создастся заново:

```sh
curl -fsSL https://raw.githubusercontent.com/alfafamily/ele/main/install.sh | bash
```

(Каталог по умолчанию — `/opt/ele`; если ставили в другой через `ELE_DIR`,
подставьте его в команды выше.)

## Резервное копирование и восстановление

### Что такое резервная копия

Резервная копия — самодостаточный архив `.tar.gz`: полный дамп базы данных (все
разделы системы) и сами файлы (аватары, файлы-реквизиты, вложения) внутри одного
файла. Из такой копии систему можно полностью развернуть заново на другом сервере.
Копия содержит чувствительные данные (в т.ч. хэши паролей) — храните и передавайте
её только по защищённым каналам; при необходимости копию можно зашифровать паролем.

### Создание копий (интерфейс)

**Настройки → Резервное копирование:**

- «Создать резервную копию сейчас» — разовый экспорт; можно задать пароль шифрования.
- «Автоматическое создание резервных копий» — ежедневно, с глубиной хранения
  (последние N копий).
- Готовую копию из «Хранилища приложения» можно скачать файлом кнопкой «Скачать».

Куда сохранять копии (единое назначение для ручных и автоматических) выбирается в
**Настройки → Системные → «Хранилище резервных копий»** радиокнопкой:
**«Хранилище приложения»** (хранилище инстанса — локальное или основной S3) либо
**«S3 для backup»** (независимое резервное хранилище, см. ниже).

### Отдельный резервный S3 (аварийная копия)

Чтобы копия пережила потерю основного сервера, её выгружают на **отдельное**
S3-хранилище (другой бакет, в идеале — другой провайдер/аккаунт). Реквизиты
задаются в `.env` (как прочие интеграции — бэкенд их только читает и проверяет
подключение из интерфейса):

```
BACKUP_S3_ENDPOINT=…
BACKUP_S3_BUCKET=…
BACKUP_S3_REGION=…
BACKUP_S3_ACCESS_KEY=…
BACKUP_S3_SECRET_KEY=…
BACKUP_PASSPHRASE=          # необязательно: пароль шифрования автоматических копий
```

Без этих параметров назначение «S3 для backup» в интерфейсе недоступно.
После изменения `.env` — перезапуск: `docker compose -f docker-compose.prod.yml up -d`.

### Восстановление (только CLI)

Восстановление выполняется **командой на сервере** (в интерфейсе не предусмотрено —
операция деструктивна) и **полностью заменяет текущее состояние** системы содержимым
копии: всё, созданное после копии, теряется. Перед заменой на непустой БД
автоматически создаётся страховочная копия. Файлы из архива раскладываются в текущее
хранилище инстанса.

Общий вид:

```sh
docker compose -f docker-compose.prod.yml exec backend \
  python manage.py restore_backup [ФАЙЛ] [опции]
```

Источник копии — один из двух:

- **Из файла** — указать путь к архиву (скачанному из интерфейса или лежащему в
  хранилище): `restore_backup /путь/к/ele-backup-….tar.gz`
- **Из резервного S3** — флаг `--from-secondary-s3` (нужны `BACKUP_S3_*`); без имени
  файла команда покажет список копий из бакета и предложит выбрать номер.

Параметры команды:

| Параметр | Назначение |
|---|---|
| `ФАЙЛ` | Путь к локальному файлу копии, либо имя объекта в резервном S3 (вместе с `--from-secondary-s3`). |
| `--from-secondary-s3` | Скачать копию из резервного S3 (`BACKUP_S3_*`). Без имени файла — интерактивный выбор из списка. |
| `--passphrase ПАРОЛЬ`, `-p` | Пароль для расшифровки зашифрованной копии (имя оканчивается на `.enc`). Если не задан — команда спросит его интерактивно. |
| `--allow-schema-mismatch` | Продолжить, даже если версия схемы (миграции) копии не совпадает с текущим инстансом. По умолчанию несовпадение останавливает восстановление. |
| `--no-safety-backup` | Не делать страховочную копию текущего состояния перед заменой. |
| `--noinput` | Без интерактивных запросов (подтверждения и выбора). Требует явно указать имя копии и, для зашифрованной, `--passphrase`. |

Примеры:

```sh
# из файла (скачанного из интерфейса)
docker compose -f docker-compose.prod.yml exec backend \
  python manage.py restore_backup /opt/ele/ele-backup-20260726-1200.tar.gz

# из резервного S3 — выбрать копию из списка
docker compose -f docker-compose.prod.yml exec backend \
  python manage.py restore_backup --from-secondary-s3

# из резервного S3, конкретная зашифрованная копия, без интерактива
docker compose -f docker-compose.prod.yml exec backend \
  python manage.py restore_backup --from-secondary-s3 \
  ele-backup-20260726-1200.tar.gz.enc --passphrase 'пароль' --noinput
```

Восстановление на новом сервере (аварийное развёртывание): поднимите инстанс **той
же версии**, что и копия (обычный запуск сам прогонит миграции на пустой БД),
пропишите в `.env` `BACKUP_S3_*` (и `BACKUP_PASSPHRASE`, если копии шифровались),
затем выполните `restore_backup --from-secondary-s3` и выберите копию.

> ⚠️ Версия схемы копии должна совпадать с версией инстанса — восстанавливайте на
> инстансе той же версии, на которой копия создана.

## Диагностика

```sh
docker compose -f docker-compose.prod.yml ps        # статус сервисов
docker compose -f docker-compose.prod.yml logs -f backend
curl -fsS https://<домен>/api/health/               # health-check API
```

### Частые проблемы

- **`429 Too Many Requests` при скачивании образов.** Лимит анонимных пулов
  Docker Hub (~100 за 6 ч на IP; на IP хостера за NAT легко исчерпан не вами).
  Решение: `docker login` под бесплатным аккаунтом (лимит 200 и привязан к
  учётке) и повторить `up -d --build`; либо подождать ~6 ч. `install.sh`
  предлагает вход и сам повторяет сборку с паузой. Для частых развёртываний —
  registry-mirror в `/etc/docker/daemon.json`.
- **HTTPS не поднимается, работает только HTTP.** Caddy получает сертификат
  Let's Encrypt автоматически при трёх условиях: A-запись домена указывает на
  IP сервера, **порты 80 и 443 открыты снаружи** (чаще всего 443 закрыт в
  firewall облачной панели/`ufw`), заход по домену, а не по IP. Причину видно
  в `docker compose -f docker-compose.prod.yml logs caddy` (строки `acme`).
- **Администратор заблокировал доступ по IP сам себе.** Ограничение доступа по
  IP (**Настройки → Компания**) проверяется до всех страниц, включая форму
  входа, — если в списке нет вашего адреса, из браузера доступ уже не вернуть.
  Сброс — только с сервера, он снимает ограничение целиком (минуя проверку):

  ```sh
  docker compose -f docker-compose.prod.yml exec backend \
    python manage.py reset_ip_allowlist
  ```

  После этого войдите в интерфейс и задайте список заново, **обязательно
  добавив свой текущий IP**.
- **Забыт пароль администратора, а почта не настроена** (сброс по ссылке из
  письма недоступен). Задать новый пароль можно с сервера, указав email
  администратора (команда спросит пароль дважды):

  ```sh
  docker compose -f docker-compose.prod.yml exec backend \
    python manage.py changepassword АДРЕС@ПОЧТА
  ```
