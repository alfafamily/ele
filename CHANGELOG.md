# Changelog

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
версионирование — [SemVer](https://semver.org/lang/ru/).

**Как выпускать релиз:** обновить `VERSION` и раздел в этом файле → закоммитить
→ поставить тег и запушить его:

```sh
git tag v1.0.0
git push origin v1.0.0
```

Пуш тега запускает workflow `.github/workflows/release.yml`, который создаёт
GitHub Release. Обновление инстансов — по `docs/INSTALL.md` («Обновление версии»).

## [1.31.16] — 2026-08-03

### Исправлено
- **Аватары и логотип компании не грузились при S3-хранилище** (битые картинки в
  свежей сессии/инкогнито; в уже открытых вкладках держались из кэша). Service
  worker (`sw.js`) перехватывал ВСЕ запросы и переотправлял их через `fetch()`, а
  такой запрос из worker'а проверяется CSP-директивой `connect-src` (`'self'` +
  капча) — тогда как аватар/логотип берутся по **прямому S3-URL** (кросс-домен),
  который разрешён в `img-src` (`https:`), но не в `connect-src`. Файлы реквизитов
  оборудования/планы помещений не страдали — они идут через same-origin прокси
  `/api/files/<id>/inline/`. Теперь SW перехватывает только same-origin запросы, а
  кросс-доменные (S3-картинки, шрифты Google) грузятся нативно под своими
  директивами. Кэширования в SW нет, перехват им ничего не давал. Правка — только
  `frontend/public/sw.js`; на локальном хранилище проявления не было (media
  same-origin).

Также — задача **B62 — непривилегированный пользователь внутри контейнеров (не
root)**. Только обвязка контейнеров; прикладной код и поведение приложения не
менялись. Обновление кумулятивное — **никаких ручных действий не требуется**.

### Безопасность
- **Рабочие процессы в контейнерах больше не работают от root.** В `backend` и
  `cron` gunicorn/цикл задач исполняются под непривилегированным пользователем
  `app` (uid 10001), в контейнере статик-сервера `frontend` Caddy — под `caddyapp`
  (uid 10001). Раньше всё работало от root внутри контейнера — при пробое процесса
  это давало полный контроль над файловой системой контейнера. Reverse-proxy Caddy
  (терминация TLS, порты 80/443) намеренно оставлен как есть — ему нужны привилегии
  для сертификатов и низких портов.
- **Апгрейд существующих инсталляций — бесшовный.** Контейнер `backend` стартует
  под root, разово приводит владельца томов `static_data`/`media_data` (в старых
  установках они принадлежат root) к пользователю `app`, применяет миграции и
  `collectstatic`, после чего **сбрасывает привилегии** на `app` (через `gosu`) —
  рабочий процесс уже непривилегированный. Поэтому обычного
  `docker compose … up -d --build` достаточно, ручной `chown` тома не нужен. На
  новых установках пустой том сразу наследует владельца `app`.
- Право Caddy в контейнере `frontend` слушать привилегированный порт `:80` выдано
  точечной файловой capability `cap_net_bind_service` на бинаре, а не запуском под
  root.

Кодревью **B55 — supply-chain и безопасность инфраструктуры/CI**. Только обвязка
(сборка/деплой/прокси), прикладной код и поведение приложения не менялись.

### Безопасность
- **GitHub Actions запинены по коммит-SHA.** Экшены (`actions/checkout`,
  `setup-node`, `setup-python`, `softprops/action-gh-release`) в `ci.yml`/
  `release.yml` использовались по плавающим тегам (`@v5` и т.п.) — тег мутабелен
  и при компрометации экшена мог бы выполнить чужой код в CI. Теперь — по SHA
  (комментарий `# vX` сохранён для читаемости и Dependabot).
- **Минимальные права токена CI.** В `ci.yml` добавлен
  `permissions: contents: read` (раньше действовал дефолт репозитория).
- **Заголовки безопасности на уровне Caddy** (`infra/Caddyfile` +
  `infra/Caddyfile.dev`): `Strict-Transport-Security`, `X-Content-Type-Options:
  nosniff`, `X-Frame-Options: SAMEORIGIN`, скрытие `Server`. Покрывают
  SPA-оболочку и статику, которые в проде отдаёт сам Caddy мимо Django (раньше
  часть заголовков ставил только Django на ответах API). На dev-стенде HSTS без
  `includeSubDomains` (поддомен общего домена).
- **Прокси-контейнер Caddy больше не получает весь `.env`** (`docker-compose.prod.yml`):
  вместо `env_file: .env` пробрасывается только нужный `SITE_ADDRESS`, а секреты
  БД/S3/VAPID в окружение прокси не попадают.

### Обновление
- Стандартное: `git pull` →
  `docker compose -f docker-compose.prod.yml up -d --build`.
- **Разово после обновления выполнить** `docker compose -f docker-compose.prod.yml restart caddy`
  — изменился `infra/Caddyfile`, а при изменении только смонтированного конфига
  `up -d` не пересоздаёт контейнер Caddy (старый inode) и новые заголовки не
  подхватятся.

## [1.31.13] — 2026-08-03

Кодревью по безопасности (без изменений в логике интерфейса): устранены
найденные замечания, поведение приложения для пользователя не меняется.

### Безопасность
- **Доступ к файлу по прямой ссылке.** Открытие файла во встроенном
  просмотрщике (`/api/files/<id>/inline/`) теперь проверяет право пользователя
  именно на этот файл — по объекту-владельцу и той же матрице видимости, что и у
  карточки: администратор/ответственный за учёт/наблюдатель видят все файлы;
  «Механик по оборудованию» — файлы карточек Оборудования, «Автомеханик» — файлы
  карточек Транспорта; рядовой сотрудник — свой аватар, файлы своего
  оборудования/транспорта и план своей парковки. Прежде эндпоинт отдавал файл
  любому авторизованному пользователю по номеру, то есть перебором можно было
  получить чужие файлы.
- **Ограничение частоты попыток входа по IP-адресу** — дополнительный слой
  поверх существующей блокировки по аккаунту (капча + временный блок). Настройка
  `LOGIN_THROTTLE_RATE` (по умолчанию `30/min`).
- **HSTS** для инстансов на HTTPS (заголовок `Strict-Transport-Security`; срок —
  `DJANGO_HSTS_SECONDS`, по умолчанию год; `0` — выключить).
- **Content-Security-Policy** для веб-оболочки — ограничивает источники
  скриптов/стилей/кадров, запрещает плагины и подмену `<base>` (защита в глубину
  от внедрения стороннего содержимого).
- **Обновлён `cryptography`** (44.0.0 → 48.0.1; применяется в шифровании
  резервных копий и Web Push) — закрыты известные уязвимости зависимости;
  попутно `py-vapid` 1.9.2 → 1.9.4.

### Исправлено
- **Инструменты: одновременные операции с остатком** (приход, выдача, возврат,
  перемещение, списание) теперь выполняются атомарно с блокировкой карточки —
  исключены потерянные обновления и рассинхрон количества при параллельных
  операциях по одному инструменту.

### Обновление
- Обновление стандартное, но **с пересборкой образов** (обновились зависимости
  backend): `git pull` → `docker compose -f docker-compose.prod.yml up -d --build`.
- Релиз меняет `infra/Caddyfile` (добавлен заголовок CSP). Команда `up -d` не
  пересоздаёт контейнер Caddy при изменении только конфига, поэтому разово
  выполните `docker compose -f docker-compose.prod.yml restart caddy` — иначе
  новый заголовок не подхватится. Новые инсталляции (`install.sh`) не затронуты.
- Новых обязательных параметров `.env` нет. Необязательные:
  `DJANGO_HSTS_SECONDS` (срок HSTS) и `LOGIN_THROTTLE_RATE` (лимит попыток входа,
  например `60/min`).

## [1.31.5] — 2026-07-31

### Исправлено
- **SIM-карты:** физическую SIM-карту больше нельзя создать без размещения. При
  переключении типа E-SIM→SIM в форме создания режим размещения мог остаться

- **Пропуска и ключи** — кнопка «Создать» больше не блокируется: незаполненный
  набор зданий/помещений/мест подсвечивается ошибкой под блоком.

## [1.13.0] — 2026-07-21

### Добавлено
- **Регламенты ТО.** Техобслуживание теперь ведётся по **регламентам**, а не по
  одной дате. Регламент содержит наименование, перечень работ/материалов (вид +
  наименование + количество) и периодичность — либо раз в N месяцев, либо
  **«по потребности»**. Два вида:
  - **Регламент типа** — создаётся в редакторе Типов оборудования и наследуется
    всем оборудованием этого типа;

    карточки.
- На карточке оборудования — сворачиваемый раздел **«Регламенты ТО»** (перед
  историей): список регламентов типа и индивидуальных с их состоянием. Регламент
  типа можно **отменить для конкретного оборудования** (перестаёт
  контролироваться) и вернуть; для регламента без назначенной даты — задать
  **дату первого ТО** (любая, не раньше сегодня).
- **Проведение ТО** переработано: сначала выбор регламента (первым пунктом —
  **«Внеплановое ТО»**), затем работы/материалы. Строки из регламента — только
  для чтения; их можно **отменить** (с обязательной причиной), а недостачу
  добавить отдельной строкой. Дата следующего ТО подставляется автоматически
  (сегодня + периодичность) и может быть сдвинута только раньше расчётной; для
  «по потребности» и внепланового ТО даты нет.
- **Индикация в списке оборудования** — по самому критичному регламенту:
  просрочено (красный), подходит (жёлтый), запланировано (зелёный); отдельно
  серый значок, если у какого-то регламента дата не задана. Фильтры: **«Дата ТО
  просрочена»**, **«Подходит дата ТО»**, **«Дата ТО не задана»**.
- **Новая роль «Ответственный за ТО»** — доступ только к разделу Оборудование
  (просмотр) и возможность **проводить ТО**; регламенты не настраивает.
- Для роли **«Ответственный за учёт»** добавлен флаг **«Ответственный за
  регламенты и проведение ТО»**: по умолчанию проведение ТО и регламенты ей
  недоступны, флаг открывает полный набор действий по ТО.
- **Флаг «Установка лицензий» у Типа оборудования.** Привязать лицензию можно
  только к оборудованию, у Типа которого включён этот флаг; иначе блок
  «Установленные лицензии» на карточке скрыт. Существующим Типам с уже
  привязанными лицензиями флаг включается автоматически.

## [1.9.0] — 2026-07-20

### Добавлено
- **Размещение объектов: рабочие места, места хранения, склад.** У Места
  (в разделе «Помещения») появился **Тип места** — *Рабочее место* или *Место
  хранения*. За рабочим местом можно закрепить нескольких сотрудников (блок
  «Рабочие места» виден на карточке сотрудника).
- **Три состояния Оборудования и Инструментов.** Объект может быть закреплён
  *за сотрудником* (мобильно), *на рабочем месте* (стационарно, без конкретного
  сотрудника) или лежать *на складе* (свободный остаток). На карточке
  оборудования — единый блок «Размещение» с кнопкой «Разместить/Переместить»;
  при создании размещение выбирается в форме. Списки оборудования получили
  фильтры «За сотрудником / На рабочем месте / На складе».
- **Свободный остаток и склады.** При откреплении Оборудования от сотрудника или
  места указывается место хранения (склад), куда оно кладётся. Для Инструментов
  свободный остаток можно раскладывать по нескольким складам (приход/списание/
  выдача — по желанию с указанием склада); склад необязателен — часть остатка
  может быть «без склада» (общий свободный остаток). На карточке инструмента
  видна разбивка «Свободно по складам» + строка «Без склада».
- **SIM за оборудованием.** Корпоративную SIM теперь можно установить в
  оборудование (например, в модем для резервного канала) — помимо закрепления за
  сотрудником. Свободная физическая SIM/пропуск/ключ хранится на складе.
- **Выбор размещения при создании.** В формах создания SIM, пропусков и ключей
  размещение выбирается сразу — *за сотрудником* или *на складе* (E-SIM — только
  за сотрудником). При создании инструмента для остатка указывается склад, а
  часть остатка можно сразу выдать сотруднику с указанием количества (в истории
  движений отражается, сколько ушло на склад и сколько сотруднику). Благодаря
  этому создание объекта прямо из карточки сотрудника сразу закрепляет его за
  ним.
- **Аппаратные лицензии на складе.** Свободный физический ключ аппаратной
  лицензии можно положить на склад (при создании и при отвязке от оборудования);
  на карточке видно текущее размещение. Программные лицензии — виртуальны, склад
  им не нужен.

### Изменено
- Открепление физических SIM/пропусков/ключей от сотрудника требует указать склад
  (место хранения), куда уходит объект. **E-SIM виртуальна** — при откреплении и
  создании склад не запрашивается.
- **Инструменты:** склад в операциях необязателен, только пока есть свободный
  остаток «без склада» (актуально сразу после обновления инстанса — существующий
  остаток можно списывать/выдавать без указания склада). Когда весь свободный
  остаток распределён по складам, склад-источник обязателен, и объём операции не
  может превышать остаток без склада.
- Кнопка «Открепить» на карточках SIM/пропуска вынесена под сведения о
  сотруднике (раньше не помещалась справа при длинном ФИО).
- **Инструменты — перемещение между складами.** На карточке в ряду с
  «Оприходовать»/«Списать» добавлена кнопка перемещения свободного остатка с
  одного склада на другой (кнопки движения теперь иконками).
- В модалках движения инструмента «Доступно» показывается для выбранного склада
  (а не суммарно по всем).
- Привязка SIM (к сотруднику/оборудованию) и пропусков/ключей (к сотруднику)
  вынесена в модальное окно — единообразно с оборудованием/лицензиями.

  строку в мобильной версии — выводится в одну строку, лишнее скрывается за «…».

## [1.0.8] — 2026-07-13

### Добавлено
- Первый вход через Яндекс ID теперь заводит связанного Сотрудника: имя и
  фамилия берутся из профиля Яндекса; если там пусто — в оба поля подставляется
  логин (часть email до «@»). Повторные входы Сотрудника не дублируют.

## [1.0.7] — 2026-07-13

### Исправлено
- При задании слишком простого пароля ошибка не показывалась (форма «висела»
  без реакции): сообщение от проверки сложности пароля уходило в
  `non_field_errors`, который формы не отображали. Теперь ошибка привязана к
  полю пароля и видна на всех формах — регистрация, сброс пароля по ссылке и
  смена пароля из Профиля. На формы также добавлен запасной баннер для
  не-полевых ошибок.

## [1.0.6] — 2026-07-13

### Исправлено
- С формы завершения регистрации по приглашению убрано лишнее поле «ФИО»: оно
  было рудиментом (на сервер не отправлялось), а данные Сотрудника теперь задаёт
  администратор при приглашении.

## [1.0.5] — 2026-07-13

### Добавлено
- Саморегистрация теперь заводит связанного Сотрудника: на форме — Фамилия и Имя
  (обязательны), Отдел и Должность (по желанию); данные маппятся в карточку
  Сотрудника, учётка сразу к нему привязана.
- Приглашение пользователя (Настройки → Пользователи): свитч «Добавить
  сотрудника» — при включении можно завести нового Сотрудника (Фамилия/Имя +
  Отдел/Должность), взаимоисключающе с выбором существующего.
- Реактивация пользователя: деактивированного можно снова включить (кнопка в
  списке) — восстанавливается вход (`is_active`); занятость сотрудника и связь
  управляются отдельно в разделе Сотрудники.

### Изменено
- Убрано письмо администраторам «новый пользователь без привязки» — теперь
  саморегистрируемые сразу привязаны к Сотруднику, и уведомление потеряло смысл.

## [1.0.4] — 2026-07-13

### Добавлено
- Настройки → Компания → «Проверка отправки почты (SMTP)»: письмо с кодом уходит
  на почту текущего администратора, ввод кода подтверждает реальную доставку
  (аналог шага проверки в мастере первичной настройки).
- Поддержка SMTP на порту 465 (implicit SSL): для порта 465 SSL включается
  автоматически, даже без `EMAIL_USE_SSL` в `.env`; явный `EMAIL_USE_SSL`
  перекрывает автоопределение. `install.sh` спрашивает режим шифрования
  (tls/ssl/none) и выводит его из порта.

### Исправлено
- Отправка приглашения «подвешивала» кнопку с лоадером, если SMTP недоступен:
  добавлен `EMAIL_TIMEOUT` (10 с), отправка обёрнута в обработку ошибок —
  теперь быстрый понятный отказ вместо зависания.
- Приглашение больше не создаёт пользователя, если письмо не удалось отправить
  (создание и отправка — в одной транзакции, при ошибке всё откатывается).

### Обновление
- Если SMTP настроен на **порт 465**, дополнительных действий не требуется — SSL
  определится автоматически. Ручной `EMAIL_USE_SSL=true` в `.env` нужен только
  для нестандартного SSL на другом порту.

### Документация
- `docs/INSTALL.md`: обновления кумулятивны — версии можно перепрыгивать (все
  миграции применятся по порядку за один проход); перед обновлением
  рекомендуется бэкап.

## [1.0.3] — 2026-07-13

### Исправлено
- При ограничении доступа по IP вместо стилизованной страницы
  показывался сырой DRF browsable-API 403. Теперь браузеру отдаётся HTML-
  страница 403 в дизайн-системе (по образцу страницы 500), API-клиенту —
  прежний JSON.

## [1.0.2] — 2026-07-13

Упрощение первичного развёртывания на «голом» сервере.

### Установка
- `install.sh`: если Docker Engine / Compose v2 не найдены, скрипт предлагает
  установить Docker автоматически (официальный `get.docker.com`, под root или
  `sudo`) вместо простого выхода с ошибкой.
- `install.sh`: открывает порты 80/443 в локальном файрволе ОС (ufw/firewalld),
  если он активен, — иначе Caddy не проходит ACME-проверку и HTTPS не
  поднимается. Облачный security group провайдера по-прежнему открывается
  вручную (о чём скрипт предупреждает).

## [1.0.1] — 2026-07-13

Хотфикс по итогам первого боевого развёртывания.

### Исправлено
- Backend навсегда оставался `unhealthy` (и не стартовал `cron` с фоновыми
  задачами): внутренний healthcheck ходит на `Host: localhost`, которого не
  было в `DJANGO_ALLOWED_HOSTS`, — Django отвечал 400. `localhost`/`127.0.0.1`
  теперь всегда в списке разрешённых хостов в проде.
- Тормоза интерфейса (скелетоны по несколько секунд): gunicorn запускался с
  одним синхронным воркером и обрабатывал запросы по одному. Число воркеров
  теперь считается от числа ядер (override — `WEB_CONCURRENCY`,
  `GUNICORN_THREADS`).

### Установка
- `install.sh` устойчив к лимиту Docker Hub (`429 Too Many Requests`):
  предлагает `docker login` и повторяет сборку с нарастающей паузой.
- `docs/INSTALL.md` — раздел «Частые проблемы» (429 при пуле образов и
  диагностика TLS/HTTPS: порты 80/443 и A-запись домена).

## [1.0.0] — 2026-07-13

Первый публичный релиз on-premise системы учёта оборудования, лицензий и
пользователей.

### Основное
- Разделы Оборудование, Лицензии, Сотрудники, Пользователи, Настройки, Профиль;
  роли Администратор / Ответственный за учёт / Сотрудник (+ «Наблюдатель»).
- Типы и динамические реквизиты (EAV), дополнительные поля, файловые реквизиты
  (встроенный просмотрщик, удаление файла).
- Аутентификация: логин/пароль, Яндекс ID, регистрация, приглашения (с
  подтверждением при чужом домене), восстановление пароля, защита от подбора.
- Списки с курсорной пагинацией и адаптивной (desktop/mobile) вёрсткой;
  двухстрочные колонки, обрезка длинного текста.
- Карточки объектов: sticky-боковой блок, действия меню «…» на мобильных,
  история изменений с диффами (что/было→стало), маскирование «Номер/ключ».
- Списание/утилизация с переводом в Архив; списание открепляет сотрудника.
- Хранилище файлов Local/S3 с фоновой миграцией; резервное копирование
  (ручное/по расписанию) и восстановление через CLI.
- Развёртывание: docker-compose (Caddy + авто-TLS), установка «одной строкой»
  (`install.sh`), CI (oxlint + backend-тесты).
